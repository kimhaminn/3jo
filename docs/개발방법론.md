## 1. 기획

### 1.1 기획서

#### 배경
제조업 공급망 관리의 복잡성이 증가함에 따라, 원청기업(현대자동차)과 벤더사(부품 협력업체) 간의 발주, 납품, 평가, 정산 업무를 통합 관리하는 디지털 플랫폼의 필요성이 대두되었다.
기존의 수작업 또는 분산된 시스템으로는 실시간 현황 파악, 납기 준수율 관리, 다단계 승인 처리에 한계가 있었다.

#### 목적
- 원청기업과 벤더사 간 발주·입찰·납품·평가·정산 프로세스를 단일 웹 플랫폼에서 통합 처리
- 실시간 KPI(납기 준수율, 진행 중 발주 수, 검토 대기 입찰 수 등) 모니터링을 통한 의사결정 지원
- 다단계 사용자 승인 체계(SCM 관리자 → 원청기업 관리자)를 통한 보안 강화
- 벤더사 평가 자동화 및 성과 보고서 제공으로 협력사 관리 효율화

#### 범위
| 구분 | 포함 범위 |
|------|-----------|
| 사용자 관리 | 회원가입, 로그인, 다단계 승인, 프로필 관리 |
| 발주 / 입찰 | 발주 등록, 발주 현황, 입찰 신청, 입찰 심사 |
| 납품 관리 | 납품 현황 목록, 납품 상세(지도 연동) |
| 공급 최적화 | 벤더별 공급 배분 최적화(유전 알고리즘) |
| 평가 / 보고 | 업체 평가, 벤더 성과 보고서 |
| 정산 | 정산 현황 |
| 공지 | 공지사항 등록 및 읽음 처리 |
| 부품 DB | 자동차 부품 데이터베이스 조회 |

---

### 1.2 고객 및 사용자 구분

| 역할 | 구분 | 설명 |
|------|------|------|
| **SCM 관리자** (`scm`) | 내부 사용자 | 시스템 전체 관리자. 사용자 승인/거절, 발주 삭제, 공지 등록, 모든 데이터 조회 가능 |
| **원청기업 관리자** (`admin`) | 내부 사용자 | 현대자동차 소속 담당자. 발주 등록, 벤더 승인, 입찰 심사, 평가 조회 가능 |
| **벤더사** (`vendor`) | 외부 사용자 | 부품 협력업체 담당자. 입찰 신청, 납품 현황 조회, 본인 평가 조회 가능 |

> 승인 흐름: 벤더사 가입 → SCM 승인 → 원청기업 승인 → 최종 APPROVED  
> 원청기업 가입 → SCM 승인 → 최종 APPROVED

## 2. 분석

### 2.1 현황 분석 (내부)

#### 기존 시스템
- 통합 SCM 웹 시스템 부재; 발주/납품 관련 업무를 이메일·엑셀로 처리
- 사용자 인증 및 권한 관리 체계 미흡 (단일 계정 공유 등)
- 납기 준수율, 벤더 평가 등 KPI 지표를 수작업으로 집계

#### 기존 프로세스
- 발주: 이메일로 발주서 전송 → 벤더사 수동 확인 → 구두/메일 회신
- 입찰: 견적서 개별 수신 → 담당자가 수동 비교·선정
- 납품 확인: 전화 또는 이메일로 납품 상태 확인
- 벤더 평가: 연 1회 수동 집계 후 보고서 작성

---

### 2.2 환경 분석 (외부)

#### 외부 시스템 연동
| 외부 시스템 | 연동 방식 | 목적 |
|-------------|-----------|------|
| **Naver Maps API** (지도 서비스) | REST API (HTTP GET) | 납품 경로 최적화, 실시간 배송 위치 지도 표시 (`delivery.jsp`, `bestroute2.jsp`) |
| **Naver Directions API** | REST API (Proxy via JSP) | 출발지 → 목적지 경로 안내 및 예상 소요시간 계산 |
| **Google Fonts** | CDN | UI 폰트(Noto Sans KR, Share Tech Mono) 제공 |
| **Font Awesome** | CDN | 아이콘 라이브러리 |

#### 외부 프로세스
- 벤더사의 사업자등록증, 법인등록증, 기술인증 서류를 시스템 외부(오프라인)에서 수집 후 시스템 내 업로드
- 정산 처리는 현재 외부 ERP/회계 시스템과 별도로 운영 (추후 연동 검토)

### 2.3 요구사항 정의

#### 기능 요구사항

| ID | 구분 | 요구사항 | 관련 화면 |
|----|------|----------|-----------|
| F-01 | 사용자 | 역할(SCM/원청/벤더)을 선택하여 회원가입할 수 있어야 한다 | `signup.jsp` |
| F-02 | 사용자 | 다단계 승인(SCM → 원청) 후 로그인이 가능해야 한다 | `login.jsp`, `adminApproval.jsp` |
| F-03 | 발주 | 원청기업은 부품 정보(이미지 포함)와 함께 발주를 등록할 수 있어야 한다 | `bidReg.jsp` |
| F-04 | 발주 | 벤더사는 진행 중인 발주 목록을 조회하고 입찰 신청할 수 있어야 한다 | `bidList.jsp`, `bidItemReg.jsp` |
| F-05 | 납품 | 납품 현황을 목록으로 조회하고 지도로 배송 경로를 확인할 수 있어야 한다 | `deliveryList.jsp`, `delivery.jsp` |
| F-06 | 평가 | SCM/원청은 벤더사를 점수 기반으로 평가하고 이력을 조회할 수 있어야 한다 | `evaluationList.jsp`, `evaluation.jsp` |
| F-07 | 공급 최적화 | 유전 알고리즘 기반으로 복수 벤더 간 최적 공급 배분을 산출할 수 있어야 한다 | `supplymgt.jsp` |
| F-08 | 공지 | SCM/원청은 역할별 타겟 공지를 등록하고 읽음 처리가 가능해야 한다 | `notice.jsp`, `noticeRead.jsp` |
| F-09 | 보고 | 벤더 성과 보고서를 화면에서 조회하고 이메일로 전송할 수 있어야 한다 | `vendorReport2.jsp` |
| F-10 | 부품 DB | 부품 코드·이름·차량 도메인 기준으로 부품 데이터베이스를 검색할 수 있어야 한다 | `parts_db_view.jsp` |

#### 품질 기준

| 품질 속성 | 기준 | 비고 |
|-----------|------|------|
| **보안성** | 모든 페이지 세션 인증 필수; 역할별 접근 제어 적용 | 미승인 사용자 로그인 차단 |
| **가용성** | 핵심 기능(발주·납품) 정상 운영 | 외부 API 장애 시 지도 기능 제외 서비스 유지 |
| **성능** | 목록 조회 응답시간 3초 이내 | 페이지네이션(20건) 적용 |
| **유지보수성** | 공통 컴포넌트(navbar, sidebar, footer) 분리 | JSP include 방식 |
| **호환성** | 최신 Chrome, Edge 브라우저 지원 | 반응형 레이아웃 적용 |

### 3.3 시스템 아키텍처

#### 기술 스택
| 계층 | 기술 |
|------|------|
| **프론트엔드** | HTML5, CSS3, JavaScript (Vanilla), JSP (View 역할) |
| **백엔드** | Java (JSP + Servlet), JDBC |
| **데이터베이스** | MySQL (`hmc_scm` 스키마) |
| **외부 API** | Naver Maps API, Naver Directions API |
| **서버** | Apache Tomcat (JSP 컨테이너) |

#### 주요 DB 테이블
| 테이블명 | 설명 |
|----------|------|
| `users` | 사용자 계정 (역할, 승인 상태 포함) |
| `vendors` | 벤더사 기업 정보 |
| `bids` | 발주 정보 |
| `bid_applications` | 벤더 입찰 신청 내역 |
| `deliveries` | 납품 현황 |
| `evaluations` | 벤더사 평가 이력 |
| `notices` | 공지사항 |
| `notice_reads` | 공지 읽음 처리 |
| `parts` | 부품 정보 |
| `parts_db` | 자동차 부품 카탈로그 DB |

#### 아키텍처 흐름
```
[브라우저]
    ↕ HTTP Request/Response
[Apache Tomcat]
    ↕ JDBC (DBUtil.getConnection())
[MySQL - hmc_scm DB]

[브라우저] ←→ [JSP (Naver API Proxy)] ←→ [Naver Maps/Directions API]
```

### 3.4 사용자 정의 및 프로세스

#### 사용자 승인 프로세스
```
벤더사/원청기업 회원가입 (status: PENDING)
    ↓
SCM 관리자 승인 (approved_by_scm = 1)
    ↓ (벤더사의 경우 추가 단계)
원청기업 관리자 승인 (approved_by_admin = 1)
    ↓
최종 APPROVED → 로그인 가능
```

#### 발주·입찰 프로세스
```
원청기업(Admin): 발주 등록 (status: OPEN)
    ↓
벤더사(Vendor): 발주 목록 조회 → 입찰 신청 (status: PENDING)
    ↓
SCM/Admin: 입찰 검토 → 낙찰 처리 (status: CLOSED)
```
